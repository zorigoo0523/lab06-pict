# Хэсэг A: Category-Partition (гараар)

## Олон алдааны давуу эрэмбэ

Нэг хүсэлтэд хэд хэдэн алдаа зэрэг байвал **from → to → amount** гэсэн дарааллаар шалгаж, эхэлж олдсон алдааг буцаана. Дотроо `ERROR_NO_FROM` → `ERROR_FROZEN`, `ERROR_NO_TO` → `ERROR_SAME_ACCOUNT`, `ERROR_BAD_AMOUNT` → `ERROR_INSUFFICIENT` → `ERROR_LIMIT` гэсэн дараалалтай. Учир нь данс байхгүй бол тухайн дансны үлдэгдэл, лимитийг шалгах боломжгүй. Тиймээс эхлээд дансны мэдээлэл, дараа нь шилжүүлэх дүнг шалгах нь зөв гэж үзсэн.

## A1. Сонголт ба төлөөлөх утгууд

| Параметр | Сонголт | Төлөөлөх утга |
|---|---|---|
| from | Valid (хүчинтэй) | A001 (идэвхтэй, USD, үлдэгдэл 1000) |
| from | Frozen (царцаагдсан) | A003 |
| from | Missing (байхгүй) | A999 |
| to | Valid | A002 (идэвхтэй) |
| to | Missing | A998 |
| to | SameAsFrom (from-той ижил) | A001 |
| amount | Normal (хэвийн) | 100 |
| amount | Smallest (хамгийн бага эерэг) | 0.01 |
| amount | Zero (≤ 0) | 0 (мөн -50) |
| amount | OverBalance (үлдэгдлээс их) | 1500 |
| amount | OverLimit (өдрийн лимитээс их) | 300 (үлдсэн лимит 200) |
| currency | Same (ижил валют) | USD |
| currency | Different (өөр валют) | EUR (1 EUR = 1.1 USD) |

**Далд орчны сонголт:** Дансны үлдэгдэл, өдрийн лимит, тухайн өдөр өмнө нь хэдийг ашигласан, валютын ханш зэрэг нь тестийн орчноос хамаарна. Энгийн тестэд A001 дансны үлдэгдлийг 1000, өдрийн лимитийг 2000, тухайн өдөр ашигласан дүнг 0 гэж авсан. OverLimit тестэд үлдэгдлийг 5000, өдрийн лимитийг 2000, тухайн өдөр ашигласан дүнг 1800 гэж тохируулсан тул 200 үлдсэн байна. Валютын хөрвүүлэлтийн жишээнд 1 EUR = 1.1 USD гэж үзсэн.

## A2. Хязгаарлалтууд

| Утга | Тэмдэглэгээ | Үндэслэл |
|---|---|---|
| from = Frozen | [ERROR] | Царцаагдсан данснаас шилжүүлэг хийх боломжгүй тул ERROR_FROZEN өгнө. |
| from = Missing | [ERROR] | Шилжүүлэх данс байхгүй тул ERROR_NO_FROM өгнө. |
| to = Missing | [ERROR] | Хүлээн авах данс байхгүй тул ERROR_NO_TO өгнө. |
| to = SameAsFrom | [ERROR] [IF from = Valid] | Ижил данс руу шилжүүлэх боломжгүй. Энэ сонголт нь from данс хүчинтэй үед утгатай. |
| amount = Zero | [ERROR] | amount тэг буюу сөрөг байж болохгүй тул ERROR_BAD_AMOUNT өгнө. |
| amount = OverBalance | [ERROR] | Хөрвүүлсний дараах дүн үлдэгдлээс их бол ERROR_INSUFFICIENT өгнө. |
| amount = OverLimit | [ERROR] | Шилжүүлэх дүн өдрийн үлдсэн лимитээс их бол ERROR_LIMIT өгнө. |
| amount = Smallest | [SINGLE] | Хамгийн бага эерэг дүнг тусад нь шалгах хязгаарын тохиолдол гэж үзсэн. |

**N → M тооцоо:**

- Бүрэн боломжит олонлог: from 3 × to 3 × amount 5 × currency 2 = **90**
- Алдааны утгууд: from 2 + to 2 + amount 3 = **7**
- [SINGLE] утга: **1**
- Бүх параметр хүчинтэй байх үеийн валютын хоёр хувилбар: **2**
- Иймээс хязгаарлалтын дараах тестийн тоо: 7 + 1 + 2 = **10**

**90 → 10**

# Хэсэг B: PICT

## B1. Браузерын жишээ (browser.model)

Ашигласан `browser.model`:

```text
Content:   Allow, Restrict, Block
Cookies:   Allow, Restrict, Block
Popups:    Yes, No
Addons:    Yes, No
Attacks:   Yes, No
Forgeries: Yes, No
```

Бүрэн боломжит хослолын тоо:

3 × 3 × 2 × 2 × 2 × 2 = **144**

PICT-ээр ажиллуулсан үр дүн:

| Хэмжээс | Файл | Мөрийн тоо |
|---|---|---:|
| 2-way | results/browser-2way.txt | **10** |
| 3-way | results/browser-3way.txt | **20** |

2-way тестээр PICT 10 мөр гаргасан. Лекц дээр гараар 9 мөрөнд багтаасан жишээтэй харьцуулахад PICT нэг мөрөөр илүү байна. Энэ нь PICT greedy алгоритм ашигладагтай холбоотой. Алгоритм тухайн үед хамрагдаагүй хослолуудыг сонгон нөхдөг боловч бүх боломжийг урьдчилан тооцож, хамгийн цөөн мөрийг заавал олох баталгаагүй.

3-way тестээр 20 мөр гарсан. Бүрэн боломжит 144 хослолтой харьцуулахад тестийн мөрийн тоо нэлээд багассан. Гэхдээ 20 мөр гарсан нь 3-way хамралт 13.9% гэсэн үг биш, харин 144 бүрэн тохиргоог бүгдийг нь туршихын оронд PICT 3-way хамралтыг хангах 20 тестийн мөр үүсгэсэн гэсэн үг.

## B2. Шилжүүлгийн модель

**transfer-nc.model — хязгаарлалтгүй хувилбар**

```text
From:     Valid, Frozen, Missing
To:       Valid, Missing, SameAsFrom
Amount:   Normal, Zero, OverBalance, OverLimit
Currency: Same, Different
```

**transfer.model — A2-ын хязгаарлалттай хувилбар**

```text
From:     Valid, Frozen, Missing
To:       Valid, Missing, SameAsFrom
Amount:   Normal, Zero, OverBalance, OverLimit
Currency: Same, Different

IF [From] <> "Valid" THEN [To] = "Valid" AND [Amount] = "Normal";
IF [To] <> "Valid" THEN [Amount] = "Normal";
```

**transfer-neg.model — ~ сөрөг утгатай хувилбар**

```text
From:     Valid, ~Frozen, ~Missing
To:       Valid, ~Missing, ~SameAsFrom
Amount:   Normal, ~Zero, ~OverBalance, ~OverLimit
Currency: Same, Different
```

PICT-ийн гаралтын харьцуулалт:

| Хувилбар | Файл | Мөрийн тоо | Happy path мөр | 2 ба түүнээс олон алдаатай мөр | Нэг мөр дэх хамгийн их алдаа |
|---|---|---:|---:|---:|---:|
| Хязгаарлалтгүй | results/transfer-nc.txt | 13 | 0 | 10 | 3 |
| Хязгаарлалттай | results/transfer.txt | 14 | 0 | 0 | 1 |
| ~ сөрөг утгатай | results/transfer-neg.txt | 16 | 2 | 0 | 1 |

Энд Frozen, Missing, SameAsFrom, Zero, OverBalance, OverLimit гэсэн утгуудыг алдааны утга гэж тооцсон. Хязгаарлалтгүй хувилбарт 10 мөрөнд хоёр буюу түүнээс олон алдаа зэрэг орсон байна. Ийм тохиолдолд эхний алдаа бусад алдааг нууж болох тул error masking үүснэ. Хязгаарлалттай болон ~ сөрөг утгатай хувилбаруудад нэг мөрөнд олон алдаа зэрэг орох асуудал гараагүй.

`~` тэмдэг ашигласнаар тухайн утгыг сөрөг утга гэж PICT-д тэмдэглэж өгдөг. Ингэснээр нэг тестийн мөрөнд хамгийн ихдээ нэг сөрөг утга ордог. Тиймээс зөвхөн олон алдааг нэг мөрөнд оруулахгүй байх зорилготой A2-ын зарим хязгаарлалт шаардлагагүй болж болно. Гэхдээ утгуудын хооронд бодит хамаарал байгаа тохиолдолд IF хязгаарлалт хэрэгтэй хэвээр байна. Жишээ нь SameAsFrom утга нь from данс хүчинтэй үед л утгатай.

## Бодит тест кейсүүд

Олон алдаатай тохиолдолд Хэсэг A-д тогтоосон **from → to → amount** гэсэн давуу эрэмбийг ашигласан.

### TC-1. Happy path

**PICT мөр:** Valid | Valid | Normal | Same

- **Setup:** A001 данс идэвхтэй, USD валюттай, үлдэгдэл 1000. A002 данс идэвхтэй. Өдрийн лимит 2000 бөгөөд тухайн өдөр ашигласан дүн 0.
- **Оролт:** `POST /transfer {"from":"A001","to":"A002","amount":100,"currency":"USD"}`
- **Oracle:** 201 `{"result":"OK"}`

### TC-2. From данс байхгүй

**PICT мөр:** ~Missing | Valid | Normal | Same

- **Setup:** A999 данс байхгүй. A002 данс идэвхтэй. A001 данс хүчинтэй, үлдэгдэл 1000.
- **Оролт:** `POST /transfer {"from":"A999","to":"A002","amount":100,"currency":"USD"}`
- **Oracle:** 200 `{"result":"ERROR_NO_FROM"}`

### TC-3. Үлдэгдэл хүрэлцэхгүй

**PICT мөр:** Valid | Valid | ~OverBalance | Different

- **Setup:** A001 данс идэвхтэй, USD валюттай, үлдэгдэл 1000. A002 данс идэвхтэй. Өдрийн лимитийн үлдэгдэл 2000. 1 EUR = 1.1 USD ханштай.
- **Оролт:** `POST /transfer {"from":"A001","to":"A002","amount":1500,"currency":"EUR"}`
- **Oracle:** 200 `{"result":"ERROR_INSUFFICIENT"}`. Учир нь 1500 EUR нь 1650 USD болж хөрвөх бөгөөд 1000 USD үлдэгдлээс их байна.

### TC-4. Нэгээс олон алдаатай нөхцөл

**PICT мөр:** Frozen | Valid | OverBalance | Same

- **Setup:** A003 данс царцаагдсан, A002 данс идэвхтэй. Шилжүүлэх дүн 1500 USD, үлдэгдэл 1000 USD.
- **Оролт:** `POST /transfer {"from":"A003","to":"A002","amount":1500,"currency":"USD"}`
- **Oracle:** 200 `{"result":"ERROR_FROZEN"}`. Учир нь from дансны алдааг to болон amount-аас өмнө шалгана гэж давуу эрэмбэ тогтоосон.

## B3. Хоёр аргын харьцуулалт

Category-Partition аргаар гараар хийсэн A3 хүснэгт нь алдааны төрлүүд, тэдгээрийн хоорондын хамаарал болон хүлээгдэх үр дүнг тодорхой харуулдаг. Тиймээс тестийн семантик болон oracle-ийг нарийн тодорхойлоход илүү тохиромжтой. Харин PICT нь параметрүүдийн хослолыг автоматаар үүсгэж, pairwise эсвэл 3-way хамралтыг хангахад тусалдаг. Гэхдээ PICT-ийн гаралт нь тестийн утгуудын хослол болохоос хүлээгдэх үр дүнг өөрөө тодорхойлдоггүй. Олон алдаатай тохиолдолд ямар алдаа түрүүлж буцахыг хүн өөрөө тогтоох шаардлагатай. Иймээс хоёр аргыг хамтад нь ашиглах нь илүү үр дүнтэй гэж үзсэн.

## Дүгнэлт

Энэ лабораторийн ажлаар Category-Partition болон PICT гэсэн хоёр аргаар тест тохиолдол боловсруулахыг туршиж үзлээ. Эхлээд шилжүүлгийн функцийн параметрүүдийг сонголт, төлөөлөх утгуудад хувааж, 90 боломжит хослолыг хязгаарлалтын дараа 10 тест болгон багасгасан. Дараа нь A3 хүснэгтэд амжилттай болон алдаатай тохиолдлуудыг оруулж, олон алдаатай үед буцах алдааны дарааллыг тогтоосон. Browser жишээн дээр PICT 2-way-д 10, 3-way-д 20 мөр үүсгэсэн. 2-way-ийн 10 мөр нь лекцийн гараар гаргасан 9 мөрөөс нэгээр олон байсан нь greedy алгоритм үргэлж хамгийн бага мөрийг олдоггүйг харуулсан. Transfer-ийн хязгаарлалтгүй хувилбарт олон алдаа нэг мөрөнд давхар орж error masking үүсэх боломжтой байв. Харин IF хязгаарлалт болон ~ сөрөг утгыг ашиглахад нэг мөрөнд олон алдаа орох асуудал арилсан. Гараар хийсэн арга нь алдааны утга, хүлээгдэх үр дүнг тодорхойлоход илүү тохиромжтой, PICT нь хослолын хамралтыг автоматаар үүсгэхэд давуу талтай байна. Энэ ажлын хамгийн их бодол шаардсан хэсэг нь олон алдааны давуу эрэмбийг тогтоох болон түүнийг PICT-ийн хязгаарлалт руу зөв буулгах байсан.
